**Status**: Root Cause FOUND (audit only, no code modified)
**Date**: 2026-08-26
**Baseline**: commit dab8f77 (P0-1.10.2)
**Method**: MSVC AddressSanitizer (/fsanitize=address)

## 1. Executive Summary

**ROOT CAUSE IDENTIFIED**: C VM has a **memory management architecture defect** — no reference counting and no copy-on-write, causing heap objects (arrays/maps/strings) to be shared by multiple TLLValue references and then double-freed.

This explains why:
- Simple programs (hello, closures) PASS — minimal value sharing
- Metacircular execution (vm_run → vm.tll → user program) CRASHES — vm.tll interpreter heavily shares data structures (constants, functions, instructions arrays)
- compiler.tllbc CRASHES with heap corruption (0xC0000374) — compiler has massive value sharing

## 3. Root Cause Analysis

### 3.1 The Defect

C VM's `TLLValue` is a struct containing pointers to heap objects (strings, arrays, maps). Assignment is **shallow copy**:

```c
frame->locals[a] = regs[b];  // copies struct, shares heap pointer
```

But `tll_value_free` **frees the heap object**:
```c
tll_value_free(frame->locals[a]);  // frees heap object
```

When the same heap object is referenced by multiple TLLValues (e.g., in registers AND locals, or passed as argument AND stored), the first free leaves dangling pointers. The second free causes use-after-free / double-free.

### 3.2 Why Simple Programs Pass

In hello.tllbc and closures.tllbc:
- Values are typically created in a register, used immediately, then not referenced again
- Minimal aliasing between registers and locals
- Arrays/maps are usually created once and not shared

### 3.3 Why Metacircular Execution Crashes

In vm.tll interpreter:
- `vm_constants = program["constants"]` — the entire constant pool array is referenced
- `vm_functions = program["functions"]` — the entire function table array is referenced
- These arrays are read repeatedly via `arrays.get(vm_constants, b)` in OP_LOAD_CONST
- When vm.tll stores values in locals/registers, the same array pointer gets shared
- OP_STORE_VAR frees the old local value, which may be the same array still referenced elsewhere
- Result: use-after-free when the freed array is accessed again

### 3.4 Same Defect in OP_STORE_GLOBAL

**vm.c:216-219**:
```c
case OP_STORE_GLOBAL:
    tll_value_free(vm->globals[a]);  // same defect
    vm->globals[a] = regs[b];
    break;
```

### 3.5 Other Affected Operations

Any operation that calls `tll_value_free` on a value that may be shared:
- OP_STORE_VAR (vm.c:210) — CONFIRMED CRASH
- OP_STORE_GLOBAL (vm.c:217) — LATENT
- OP_SET_UPVALUE (vm.c:250) — LATENT (`tll_value_free(upvalue->value)`)
- free_frame (vm.c:78-84) — LATENT (frees all locals, which may be shared with registers)
- RET (vm.c:364-372) — LATENT (free_frame after return)

## 5. Fix Options (for future implementation, NOT done in this audit)

### Option A: Reference Counting
- Add `refCount` to all heap objects (TLLArray, TLLMap, TLLString)
- Assignment increments refCount
- tll_value_free decrements refCount, frees only when 0
- Pros: Deterministic, no GC pauses
- Cons: Need to handle cycles (maps containing maps), invasive changes

### Option B: Deep Copy on Assignment
- `frame->locals[a] = tll_value_deep_copy(regs[b])`
- Pros: Simple ownership model, no cycles
- Cons: Performance overhead (large arrays copied frequently), high memory usage

### Option C: Garbage Collection (tracing)
- Remove all tll_value_free calls
- Implement mark-sweep or copying GC
- Pros: Handles cycles, no ref count overhead
- Cons: Complex implementation, GC pauses, needs root set enumeration

### Option D: Borrowed References (minimal fix)
- Distinguish "owned" vs "borrowed" TLLValue
- Only free owned values
- Pros: Minimal changes
- Cons: Error-prone, requires careful annotation

**Recommended**: Option A (reference counting) for v1.1 — matches the existing UpvalueBox refCount pattern, deterministic, handles the common case. Cycle collection can be deferred.

## 8. Conclusion

The Native VM crash is **NOT** caused by:
- ❌ Closure env loss (P0-1.10 misdiagnosis, corrected in P0-1.10.2)
- ❌ Opcode implementation errors (45/46 are correct)
- ❌ Builtin missing (91/98, but crash is before any builtin call in metacircular path)

The crash IS caused by:
- ✅ **Memory management defect**: no reference counting, heap objects shared then double-freed
- ✅ First crash point: OP_STORE_VAR at vm.c:210
- ✅ Trigger: value sharing in vm.tll interpreter (constants/functions arrays)

**Root cause located. Call chain established. First illegal operation identified.**
