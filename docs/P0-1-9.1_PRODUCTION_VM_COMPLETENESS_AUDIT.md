# P0-1.9.1 Production VM Completeness Audit

**状态**: 已完成审计，待验收
**日期**: 2026-08-26
**基线**: v1.1-language-core-freeze / tllos commit 1c32d9c
**审计范围**: Native tllvm (C) vs TLL Reference VM (vm.tll) 语义等价性

---

## 1. Executive Summary

### 1.1 核心结论

**Native tllvm 当前状态：Experimental Bootstrap VM，不能宣布为 Production VM。**

| 维度 | TLL Reference VM | Native tllvm | 等价性 |
|------|-----------------|--------------|--------|
| Opcode 覆盖 | 46/46 | 45/46 | ⚠️ 缺 OP_MAKE_STRUCT |
| Builtin 覆盖 | 98/120 (0-97) | 91/120 (0-90) | ⚠️ 缺 http (91-97) |
| 直接执行用户程序 | ✅ | ✅ (部分) | ⚠️ 仅验证 8 个测试 |
| 元循环执行 vm.tll | ✅ | ❌ 崩溃 | 🔴 未通过 |
| 执行 compiler.tllbc | ✅ | ❌ 崩溃 | 🔴 未通过 |
| 完整 32/32 测试套件 | ✅ | ❌ 未验证 | 🔴 未验证 |
| Differential Testing | — | — | 🔴 不存在 |

### 1.2 关键发现

1. **C VM 能直接执行简单/中型 TLL 程序**：hello、closures、hof、mut_closure、min_closure、simple_fn、fs.readFile、json.parse 均通过。
2. **C VM 元循环执行失败**：`tllvm → vm_run.tllbc → vm.tll → user.tllbc` 路径在 vm.run() 处理包含函数的程序时崩溃，连极简程序（1函数0指令）都崩溃。
3. **C VM 直接执行 compiler.tllbc 失败**：580KB / 152函数 / 18463指令的编译器 bytecode 在 C VM 中加载后执行崩溃（堆损坏 0xC0000374）。
4. **不存在 Differential Testing**：没有自动化测试验证同一 bytecode 在两套 VM 上输出一致。
5. **OP_MAKE_STRUCT (27) 未实现**：C VM 中无此 opcode 的 case。
6. **HTTP builtin (91-97) 未实现**：C VM 只覆盖到 builtin 90 (fs)。

### 1.3 架构判定

ADR-001 方案 B（Native tllvm = 唯一生产 VM）**当前不满足验收条件**。

Native tllvm 必须保持 **Experimental Bootstrap VM** 定位，直到：
- 46/46 opcode 等价
- 98/98 builtin 等价（或明确 http 为 deferred）
- compiler.tllbc 可在 C VM 中自举执行
- 完整 32/32 测试在 C VM 中通过
- Differential Testing 套件建立并通过

### 3.2 已知 Value Model 差异

1. **字符串编码**: TLL VM 使用 JS UTF-16 字符串，C VM 使用 UTF-8 C 字符串。`strings.charAt`、`strings.length` 对非 ASCII 字符可能行为不同。
2. **数字精度**: TLL VM 使用 JS double（53位整数精度），C VM 使用 long long（64位）。大整数运算可能溢出行为不同。
3. **Map 迭代顺序**: TLL VM 使用 JS object（插入顺序），C VM 使用 hash table（不保证顺序）。`json.stringify` 输出的键顺序可能不同。
4. **数组长度**: TLL VM 中数组 length 是动态属性，C VM 中是 struct 字段。行为应一致，但需验证。

## 8. Architecture Decision

### 8.1 当前判定

**Native tllvm = Experimental Bootstrap VM（实验性启动 VM）**

**TLL Reference VM (vm.tll) = Reference / 自举验证 VM**

ADR-001 方案 B（Native tllvm = 唯一生产 VM）**暂不批准**，原因：
- 未证明 46/46 opcode 等价
- 未证明 98/98 builtin 等价
- 未证明完整 32/32 测试通过
- 元循环执行和 compiler 自举均失败
- 不存在 Differential Testing

### 8.2 可选路径

#### 路径 1: 补齐 Native tllvm 成为 Production VM

**工作内容**:
1. 修复元循环执行崩溃（vm.run 处理有函数的程序）
2. 修复 compiler.tllbc 执行崩溃（堆损坏）
3. 实现 OP_MAKE_STRUCT
4. 实现 HTTP builtin（或明确标记 deferred）
5. 在 C VM 中运行完整 32/32 测试套件并修复所有失败
6. 建立 Differential Testing 框架
7. 验证 A==B==C 自举在 C VM 中通过

**预估工作量**: 大（可能需要数周）
**风险**: C VM 可能持续膨胀为第二套完整 Runtime

#### 路径 2: 保持双 VM 架构，明确分工

**架构**:
```
生产路径: tllvm (C) → 用户 .tllbc → 直接执行
参考路径: vm.tll (TLL) → Reference VM / 自举验证
```

**工作内容**:
1. 明确 tllvm 为 Production VM，vm.tll 为 Reference VM
2. 建立 spec/ 作为唯一事实来源（OPCODES.json, BYTECODE.md, VALUE_MODEL.md）
3. 建立 Differential Testing 强制两套 VM 输出一致
4. 逐步补齐 C VM 缺失能力
5. 每次语言特性变更必须同时更新两套 VM 和 spec

**预估工作量**: 中
**风险**: 双 VM 维护成本，但有 spec 约束可降低分叉风险

#### 路径 3: 重新设计第一把火

**思路**: 不要求 C VM 执行完整 TLL 语义，而是设计一个最小的 Stage-0 loader，只负责加载 vm_run.tllbc 并将执行权交给 TLL VM。

**问题**: 这正是当前尝试的元循环路径，已经失败。要让它工作，C VM 仍然需要能够正确执行 vm.tll 的全部 bytecode 语义。

**结论**: 路径 3 本质上等同于路径 1 的元循环部分，不可行。

### 8.3 推荐

**推荐路径 2: 保持双 VM 架构，以 spec 为唯一事实来源。**

理由:
1. C VM 已能直接执行大部分用户程序，证明这条路可行
2. 双 VM 提供交叉验证能力，提高语言可靠性
3. spec 驱动开发可避免语义分叉
4. vm.tll 作为纯 TLL 参考实现，是语言独立性的重要证明
5. 渐进式补齐 C VM 比一次性修复元循环更可控
