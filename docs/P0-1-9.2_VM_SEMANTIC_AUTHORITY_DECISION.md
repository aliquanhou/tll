## 1. 问题定义

### 1.1 核心问题

> **TLL OS 最终到底需要一个 VM，还是两个 VM？**

### 1.2 当前事实基线

| 项目 | 状态 |
|------|------|
| TLL v1.1 Language Core | FROZEN |
| TLL Compiler (纯 TLL) | 自举 A==B==C |
| TLL Reference VM (vm.tll, 纯 TLL) | 46/46 opcode, 98 builtin, 32+ 测试通过 |
| Native tllvm (C) | Experimental, 45/46 opcode, 91 builtin, 9 测试验证 |
| Production Executor | UNDECIDED |

### 1.3 四层概念澄清

| 层次 | 定义 | 示例 | 数量 |
|------|------|------|------|
| Opcode | bytecode 指令 | LOAD_CONST, CALL, CLOSURE | 46 (0-45), 已冻结 |
| Compiler Intrinsic | 编译器内联为 opcode 的调用 | io.println->OP_PRINTLN, io.print->OP_PRINT | 2 个已知 |
| Language-level Builtin | 用户可调用的标准库函数 | json.parse, math.sqrt, fs.readFile | 98 个已定义 (0-97) |
| Host ABI | VM 与 OS 交互的接口分类 | io, fs, http, process, env | 6 个类别 |

**数据纠正**: 不是 "98/120 builtin"，而是 98 个已定义 builtin semantic (idx 0-97)。idx 98-119 是预留 slot (agent/workflow)，双方均未实现，属于 deferred。实际差距是 98 vs 91 = 7 个 (http 模块, idx 91-97)。

## 2. 三种架构方案深度分析

### 方案 A: TLL Reference VM (vm.tll) 作为唯一语义权威

**架构**: TLL Source -> TLL Compiler -> TLL Bytecode -> TLL VM (vm.tll) -> 用户程序

**第一把火问题**: vm.tll 本身是 TLL 程序，需要外部执行器启动。可选: A1 最小 C Loader 元循环执行 (当前已失败); A2 AOT 预编译; A3 外部运行时 (Node.js)。

**优点**: 语言纯粹性最强; 单一实现无分叉; 维护成本最低; 自证完备。

**缺点**: 第一把火未解决 (元循环崩溃); 双层解释性能差; 调试困难; 当前阻塞。

**可行性**: 理论可行，当前阻塞 (元循环失败)，工程复杂度高。

### 方案 B: Native VM (tllvm, C) 作为唯一语义权威

**架构**: TLL Source -> TLL Compiler -> TLL Bytecode -> Native VM (tllvm, C) -> 用户程序

**vm.tll 角色**: Reference / 自举验证 / 规范可执行版本，非生产路径。

**优点**: 性能最优; 启动简单无第一把火问题; 部署最简单; 0 JS/TS 直接可达; 当前已有基础。

**缺点**: 当前不完整 (45/46 opcode, 91/98 builtin); 补齐工作量大; C 代码维护成本; vm.tll 生命周期需明确。

**vm.tll 长期生命周期**: 当前->v1.2 Reference VM; v1.2->v2.0 Differential 对照(可选); v2.0+ 规范可执行版本/教育用途; 可选迁移至独立仓库。

**可行性**: 部分可行 (简单程序通过)，理论可行，工程复杂度中高。

### 方案 C: 双 VM 规范实现，必须 Differential-Equivalent

**架构**: TLL Specification (spec/ 唯一权威) -> 两套实现 (TLL VM + Native VM) -> Differential Testing 强制一致

**优点**: 交叉验证提高可靠性; 性能与纯粹性兼得; 规范驱动避免实现即规范; 行业有先例 (Python/Ruby/Lua)。

**缺点**: 维护成本最高 (3 处修改: spec + 2 实现); 一致性保证困难; 当前差距大; 分叉风险。

**长期一致性机制**: Differential Testing + Fuzz Testing + Spec Compliance Test + CI 强制。

**可行性**: 当前不可行 (Differential Testing 不存在, Native VM 不完整)，理论可行，工程复杂度很高。

## 5. 推荐决策

### 推荐: 方案 B（带约束）

**Native tllvm = Production VM（唯一生产执行器）**
**vm.tll = Reference VM / 自举验证 / 规范可执行版本**
**spec/ = 语义参考（不强制双 VM differential-equivalent）**

### 不是 sunk-cost 论证，而是因为：

1. 第一把火有干净解: 原生二进制直接加载 .tllbc，无需元循环
2. 性能可接受: 单层 C 解释器
3. 0 JS/TS 直接可达: 纯 C 实现
4. 部署最简单: 用户下载一个二进制即可
5. vm.tll 仍保留: 永久证明自举能力，用于原型验证
6. 当前已有基础: C VM 已能执行大部分简单/中型程序

### 反对意见与回应

**"C 代码难维护"**: vm.tll 仍存在并维护作为 Reference。生产用 C 是性能和部署考量，不是 TLL 不能写 VM。

**"双 VM 会分叉"**: 方案 B 不是双生产 VM。vm.tll 是 Reference 不是生产。用户程序只在 Native VM 运行。语义权威是 spec/。

**"应该先解决元循环"**: 元循环已投入大量时间未解决，且双层解释性能不可接受。Native VM 直接执行已验证可行，补齐更可控。

**"这是 sunk-cost"**: 选择 Native VM 不是因为已写 C 代码，而是因为 Native 路径有干净的第一把火解、更好性能、更简单部署。从零开始也会选 Native。
