## 1. Executive Summary

**KEY CORRECTION**: P0-1.10's finding #1 ("map-load closure env loss") is a **MISDIAGNOSIS**.

Function Values are **NOT stored in the constant pool**. `spec/BYTECODE.md` is correct. All Function Values are created dynamically at runtime. The C VM's map→function conversion in do_call only handles env=null cases (top-level functions, non-capturing nested functions), which is correct. The metacircular execution crash has a different root cause that remains unidentified.

## 2. Function Value Creation — Complete Evidence Chain

### 2.1 Compiler: Top-Level Functions

**Source**: `compiler/codegen.tll` lines 391-430

```tll

// create {__fn:true, fnIdx:fvi, env:null} for TOP-LEVEL functions only

let v1 = cg_allocReg()
cg_emit(OP_LOAD_CONST, [v1, cg_addConstant(true)])

cg_emit(OP_STORE_GLOBAL, [gIdx, fnValReg])
```

**Conclusion**: Top-level function values are created at runtime in `__main__` via OP_MAKE_MAP. env is always null. NOT stored in constant pool.

**Source**: `compiler/codegen.tll` lines 638-650

**Verdict**: BYTECODE.md is **CORRECT**. There is NO Spec-Implementation mismatch on this point.

## 3. C VM: Function Value Handling

### 3.1 OP_CLOSURE creates TLL_FUNCTION (not map)

**Source**: `host/c/vm.c` lines 255-271

```c
case OP_CLOSURE: {
    int captureCount = c;
    TLLClosureEnv *newEnv = ...;
    // ... copy upvalue references from frame->closureEnv ...
    regs[a] = tll_function(b, newEnv);  // Native TLL_FUNCTION, NOT a map
    break;
}
```

**Conclusion**: C VM's OP_CLOSURE creates a native TLL_FUNCTION with proper env. No map involved. env is correct.

### 3.2 do_call: map→function conversion

**Source**: `host/c/vm.c` lines 122-140

```c
if (fnIdx >= 100000) {
    /* Indirect call */
    int regNum = fnIdx - 100000;
    TLLValue possibleFn = frame->registers[regNum];
    if (possibleFn.type == TLL_MAP) {
        TLLValue fnFlag = map_get(possibleFn.as.map, "__fn");
        if (fnFlag.type == TLL_BOOL && fnFlag.as.boolean) {
            TLLValue idxVal = map_get(possibleFn.as.map, "fnIdx");
            int actualFnIdx = ...;
            TLLValue envVal = map_get(possibleFn.as.map, "env");
            TLLClosureEnv *env = NULL;
            if (envVal.type != TLL_NULL) {
                env = (TLLClosureEnv*)calloc(1, sizeof(TLLClosureEnv));  // EMPTY env!
                env->capacity = 1;
                env->upvalues = (TLLUpvalue**)calloc(1, sizeof(TLLUpvalue*));
            }
            possibleFn = tll_function(actualFnIdx, env);
        }
    }
    // ... dispatch by type ...
}
```

**Analysis**:
- This code handles map-form function values from indirect calls
- Map-form function values are ONLY created by OP_MAKE_MAP for top-level and non-capturing nested functions
- Those ALWAYS have env=null
- Therefore the `envVal.type != TLL_NULL` branch is **never triggered** by current compiler output
- The "empty env" bug is a **LATENT BUG** but does not affect current programs

**Conclusion**: The map→function conversion does NOT cause env loss in practice. P0-1.10 finding #1 is a misdiagnosis.

## 4. Semantic VM (vm.tll): User Function Values

### 4.1 vm.tll creates map-form user function values

**Source**: `runtime/vm.tll` line 293

```tll
// OP_CLOSURE handler in vm.tll interpreter:
vm_setReg(a, { __fn: true, fnIdx: b, env: newEnv })
```

**Critical**: When vm.tll interprets a user program's OP_CLOSURE, it creates a **TLL map** `{__fn:true, fnIdx:b, env:newEnv}` to represent the user's closure. This is NOT a C VM TLL_FUNCTION — it's a TLL_MAP that lives inside the vm.tll interpreter's data space.

### 4.2 vm.tll reads env via map access

**Source**: `runtime/vm.tll` lines 548-553

```tll
// Indirect CALL handler in vm.tll interpreter:
if isIndirect && possibleFn["__fn"] == true {
    actualFnIdx = possibleFn["fnIdx"]
    callClosureEnv = possibleFn["env"]  // Map access, NOT C VM do_call
}
```

**Conclusion**: vm.tll reads the user function's env via TLL map access (`possibleFn["env"]`), which is handled by C VM's INDEX_GET opcode. This works correctly. The C VM's do_call is NOT involved in user program function calls during metacircular execution.

## 5. Metacircular Execution: Actual Data Flow

```
tllvm (C VM)
  │
  ├─ loads vm_run.tllbc
  │
  ├─ executes vm_run.tll:
  │   ├─ fs.readFile("vm_run_target.tllbc")  → user bytecode as string
  │   ├─ json.parse(source)                  → user program as TLL map/list
  │   └─ run(program)                        → calls vm.tll interpreter
  │
  └─ executes vm.tll interpreter (run function):
      ├─ reads user program instructions (TLL data)
      ├─ for OP_CLOSURE: creates TLL map {__fn, fnIdx, env}  ← user function value
      ├─ for indirect CALL: reads env via map access          ← works correctly
      ├─ for user function body: simulates execution
      └─ ALL of this is C VM executing vm.tll's TLL bytecode
```

**Key insight**: During metacircular execution, there are TWO levels:
1. **C VM level**: executes vm.tll's bytecode. vm.tll's own functions are top-level (env=null) or OP_CLOSURE-created TLL_FUNCTION.
2. **vm.tll interpreter level**: simulates user program. User function values are TLL maps created by vm.tll's OP_CLOSURE handler.

The C VM's do_call map→function conversion only handles level 1 (vm.tll's own functions), which all have env=null. User program function calls (level 2) are handled by vm.tll's interpreter code via map access, not by C VM's do_call.

**Therefore**: The "empty env" in C VM's do_call is NEVER reached during metacircular execution. It is NOT the root cause of the crash.

### Suspected areas for crash root cause:

1. **C VM memory management**: heap corruption suggests buffer overflow or use-after-free in C VM
2. **Deep recursion**: compiler.tllbc has deep call chains; C VM may have stack overflow or frame allocation bugs
3. **vm.tll interpreter specific opcodes**: some opcode in vm.tll's bytecode may trigger a C VM bug not seen in simple programs
4. **Large constant pool**: compiler.tllbc has 3867 constants; constant loading or string handling may have bugs
5. **OP_MAKE_MAP with many entries**: vm.tll creates large maps for user program representation
