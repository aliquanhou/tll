---

## 1. Classification Definitions

| Classification | Meaning |
|----------------|---------|
| **SPEC VIOLATION** | Behavior explicitly contradicts a v1.1 Spec clause |
| **IMPLEMENTATION BUG** | C VM code has a bug (crash, wrong logic) regardless of Spec detail |
| **DEFERRED FEATURE** | Spec explicitly marks as "not in v1.1" or "reserved" |
| **IMPLEMENTATION CHOICE** | Spec allows multiple approaches; current choice is valid |
| **TEST GAP** | No test coverage; cannot confirm pass/fail |
| **SPEC GAP** | Spec does not define required behavior; needs spec amendment |
| **SPEC-IMPL MISMATCH** | Spec says one thing, actual compiler does another |

## 2. Finding-by-Finding Verification

### Finding #1: Map-load closure env loss

**P0-1.10 Claim**: do_call (vm.c:132-138) creates empty ClosureEnv when converting map→function, losing upvalues.

**Spec Check**:
- `spec/CLOSURE.md` §2: FunctionValue must have `env: ClosureEnv | null`
- `spec/CLOSURE.md` §3: ClosureEnv.upvalues must contain UpvalueBox references
- `spec/BYTECODE.md` §4: "Function values are NOT stored in the constant pool. They are created at runtime via LOAD_CONST for fnIdx + function value construction, or via CLOSURE opcode."

**Critical Discovery**: BYTECODE.md says function values are NOT in constant pool. But the actual TLL compiler DOES store function values as maps `{"__fn":true, "fnIdx":N, "env":...}` in the constant pool. This is a **SPEC-IMPL MISMATCH**.

**Verification**:
- Actual compiler behavior: Function values ARE serialized as maps in constants
- C VM do_call handles this by detecting `__fn` flag and converting map→TLL_FUNCTION
- The conversion creates an EMPTY env instead of deserializing upvalues from the map
- This causes closures loaded from constants to lose their captured environment

**Classification**: **IMPLEMENTATION BUG** (C VM fails to deserialize env from map) + **SPEC-IMPL MISMATCH** (BYTECODE.md contradicts actual compiler behavior)

**Severity**: P0 (blocks metacircular execution and self-hosting)

**Production Gate**: BLOCKS — must fix before Native VM can execute compiler.tllbc

**Resolution Path**:
- Option A: Fix C VM to deserialize upvalues from map env (align with actual compiler)
- Option B: Amend BYTECODE.md to document that function values ARE stored as maps in constants (align Spec with reality)
- Both needed: fix C VM bug AND correct Spec

### Finding #2: compiler.tllbc heap corruption (0xC0000374)

**P0-1.10 Claim**: Running compiler.tllbc (580KB, 152 functions, 18463 instructions) causes heap corruption.

**Spec Check**: No Spec clause — this is a runtime stability issue.

**Verification**:
- Reproduced: `tllvm.exe compiler/compiler.tllbc` crashes with 0xC0000374
- Root cause NOT yet identified — could be any of:
  - Buffer overflow in register allocation (fixed: 256→4096 dynamic)
  - Use-after-free in frame/closure lifecycle
  - Integer overflow in operand indexing
  - Stack overflow in deep recursion (compiler has deep call chains)
  - The map-load env bug causing corrupted state downstream

**Classification**: **IMPLEMENTATION BUG** (root cause unknown)

**Severity**: P0 (blocks self-hosting)

**Production Gate**: BLOCKS — must fix before Native VM can self-host

**Note**: Finding #1 (map-load env loss) is a strong candidate for root cause. When vm.tll or compiler.tllbc creates and passes function values through constants, the empty env causes corrupted closure state that may lead to heap corruption downstream.

### Finding #3: No Garbage Collection

**P0-1.10 Claim**: Native VM has no GC; manual malloc/free with leak-on-exit.

**Spec Check**:
- `spec/VALUE_MODEL.md` §9: "All heap values (strings, arrays, maps, closures) are garbage collected"
- `spec/VALUE_MODEL.md` §9: "Native VM implementations may use reference counting, mark-sweep, or other GC"
- `spec/VALUE_MODEL.md` §9: "Programs must not depend on GC timing or finalization order"

**Verification**:
- Spec REQUIRES GC (some form)
- Spec does NOT mandate a specific GC algorithm
- C VM currently has NO GC at all (only explicit free in some paths)
- UpvalueBox has refCount, but arrays/maps/strings/functions are never freed during execution

**Classification**: **SPEC VIOLATION** (no GC at all) — GC algorithm is IMPLEMENTATION CHOICE, but having none violates Spec

**Severity**: P1 for short-running programs, P0 for long-running services

**Production Gate**: CONDITIONAL — acceptable for CLI tools (process exits, OS reclaims memory); BLOCKS for long-running daemons/servers

**Note**: User correctly pointed out that "no GC" ≠ "wrong GC algorithm". The violation is the ABSENCE of any reclamation, not the choice of algorithm.

### Finding #4: AND/OR not short-circuit

**P0-1.10 Claim**: vm.c:351-352 evaluates both operands before AND/OR.

**Spec Check**:
- `spec/OPCODES.md` opcode 15: "r1 = (r2 && r3) short-circuit"
- `spec/OPCODES.md` opcode 16: "r1 = (r2 || r3) short-circuit"
- `spec/SYNTAX.md` §5.1: "&& — logical AND (short-circuit)", "|| — logical OR (short-circuit)"

**Verification**:
- C VM: `regs[a] = tll_bool(tll_truthy(regs[b]) && tll_truthy(regs[c]))`
- Both regs[b] and regs[c] are already evaluated before this line (they're computed by previous instructions)
- Wait — in a register VM, operands are ALWAYS pre-evaluated. Short-circuit must be implemented at the CODEGEN level, not the VM level.
- The compiler should emit: evaluate left → JMP_IF_FALSE → evaluate right → AND
- If the compiler emits both evaluations before AND, then short-circuit is already broken at the bytecode level, not the VM level.

**Classification**: **SPEC VIOLATION** — but the violation may be in the compiler (codegen), not the VM. Need to verify actual bytecode output.

**Severity**: P1 (side effects in right operand differ from spec)

**Production Gate**: BLOCKS for programs with side-effectful conditions

**Note**: This needs verification of actual bytecode. If compiler correctly emits JMP_IF_FALSE for short-circuit, then VM's AND is just a final boolean combine and is correct. If compiler evaluates both operands first, it's a compiler bug.

### Finding #5: MEMBER_GET NULL dereference on function values

**P0-1.10 Claim**: vm.c:447-448 passes NULL to map_get when obj is TLL_FUNCTION/TLL_BUILTIN.

**Spec Check**:
- `spec/OPCODES.md` opcode 30: "r1 = r2.name (constant name from pool)" — no type restriction specified
- `spec/VALUE_MODEL.md`: No section defining member access on function values
- `spec/SYNTAX.md`: `obj.property` syntax — no restriction on obj type

**Verification**:
- C VM code: `map_get((obj.type==TLL_MAP)?obj.as.map:NULL, propName)` — when obj is function, passes NULL
- map_get with NULL likely crashes (NULL dereference)
- Spec does NOT define what `fnValue.property` should return
- Semantic VM (JS): function values are objects `{__fn, fnIdx, env}`, so `.fnIdx` would return the fnIdx, `.env` would return env

**Classification**: **IMPLEMENTATION BUG** (crash instead of graceful behavior) + **SPEC GAP** (Spec doesn't define function member access)

**Severity**: P2 (only crashes if code accesses properties on function values, which is rare)

**Production Gate**: Does NOT block basic production use, but crashes on valid TLL code

### Finding #6: No finally execution

**P0-1.10 Claim**: throw_exception (vm.c:87-113) does not execute finally blocks during unwinding.

**Spec Check**:
- `spec/LANGUAGE.md` §1.2: "Exception System (try/catch/finally/throw) | FROZEN"
- `spec/SYNTAX.md` §6: "finally — always executes, even on return or throw"
- `spec/OPCODES.md`: TRY_START (38), TRY_END (39), THROW (37) — no OP_FINALLY

**Verification**:
- Spec explicitly includes finally in v1.1 FROZEN features
- C VM implements try/catch but skips finally
- The opcode set has no dedicated FINALLY opcode — finally is likely implemented as code emitted after try/catch blocks by the compiler
- If compiler emits finally code as normal instructions after TRY_END, then VM doesn't need special finally handling — but throw_exception must still execute that code during unwinding

**Classification**: **SPEC VIOLATION** (finally is FROZEN in v1.1, C VM doesn't execute it on throw)

**Severity**: P1 (exception handling semantics incomplete)

**Production Gate**: BLOCKS for programs using finally with exceptions

### Finding #7: OP_MAKE_STRUCT (27) not implemented

**P0-1.10 Claim**: No case for opcode 27 in C VM switch.

**Spec Check**:
- `spec/OPCODES.md` opcode 27: "MAKE_STRUCT — Create struct (reserved, not fully in v1.1)"
- `spec/LANGUAGE.md`: No "struct" type in type system (types: int, float, string, bool, null, array, map, fn)

**Verification**:
- Spec explicitly marks MAKE_STRUCT as "reserved, not fully in v1.1"
- Language type system has no struct type
- Compiler likely never emits MAKE_STRUCT in v1.1

**Classification**: **DEFERRED FEATURE** (explicitly reserved, not required for v1.1)

**Severity**: N/A for v1.1 conformance

**Production Gate**: Does NOT block v1.1 production use

### Finding #9: MOD int-only, LE/GE numeric-only

**P0-1.10 Claim**: MOD (opcode 7) only handles int; LE (13)/GE (14) only handle numeric.

**Spec Check**:
- `spec/OPCODES.md` opcode 7: "r1 = r2 % r3" — no type restriction
- `spec/OPCODES.md` opcode 13: "r1 = (r2 <= r3)" — no type restriction
- `spec/OPCODES.md` opcode 14: "r1 = (r2 >= r3)" — no type restriction
- `spec/VALUE_MODEL.md`: No explicit type coercion rules for these operators

**Verification**:
- C VM MOD: `regs[a] = tll_int(regs[b].as.integer % regs[c].as.integer)` — crashes on float (wrong union access)
- C VM LE/GE: converts to double — works for int/float but NOT strings
- Semantic VM (JS): % works on numbers (int/float), <= / >= works on strings too (lexicographic)
- LT (11) and GT (12) in C VM DO handle strings

**Classification**: **SPEC VIOLATION** (MOD crashes on float; LE/GE don't support strings like LT/GT do) — but Spec is vague on type support

**Severity**: P2 (only affects float modulo and string <= / >=)

**Production Gate**: Does NOT block most programs

## 4. True P0 Blockers for Production

Only **2 findings** are unconditional P0 blockers:

1. **#1 Map-load env loss** — blocks all programs with closures passed through constants (includes compiler, vm.tll)
2. **#2 compiler.tllbc crash** — blocks self-hosting (likely caused by #1)

**#3 No GC** is conditional: acceptable for short-lived CLI tools, blocks long-running services.

All others are P1/P2 or deferred/test gaps.

## 5. Spec Amendments Needed

Before fixing C VM, these Spec issues should be resolved:

| Spec Issue | Current State | Needed Action |
|------------|--------------|---------------|
| Function values in constant pool | BYTECODE.md says "NOT stored", but compiler stores them as maps | Amend BYTECODE.md to document actual map serialization format, OR change compiler to not store function values in constants |
| MEMBER_GET on function values | Undefined | Define behavior (return null? expose fnIdx/env? throw?) |
| GC requirement | "All heap values are garbage collected" | Clarify if leak-on-exit is acceptable for short-lived processes |
| HTTP builtins on restricted platforms | FROZEN 0-97 | Allow "not implemented" exception for network on platforms without sockets |
| AND/OR short-circuit in register VM | Spec says short-circuit, but register VMs pre-evaluate operands | Document that short-circuit is compiler responsibility (JMP_IF_FALSE), not VM opcode responsibility |

---

## 6. Recommended Fix Order

If proceeding to fix Native VM:

1. **Resolve Spec-Impl Mismatch** (#1): Amend BYTECODE.md OR change compiler. Then fix C VM env deserialization.
2. **Re-test compiler.tllbc** (#2): Likely fixed by #1. If not, debug remaining crash.
3. **Verify AND/OR bytecode** (#4): Check if compiler correctly emits JMP_IF_FALSE. If yes, close as non-issue. If no, fix compiler.
4. **Implement finally** (#6): Add finally execution to throw_exception.
5. **Add GC or document leak-on-exit** (#3): Decide production scope.
6. **Fix MEMBER_GET** (#5): Return null instead of crashing on non-map objects.
7. **Fix MOD/LE/GE** (#9): Add float modulo and string comparison.
8. **Implement HTTP or mark platform-optional** (#8).
9. **Run full 32/32** (#10).
10. **Verify A==B==C** (#11).

**No code was modified in this audit.**
